# 就绪门槛

用这道门槛判断应该实施、提问还是停止。它衡量的是未解决风险，不是模型的主观信心。

## 对未知项分类

将每个未知项归入一类：

- **阻塞项：** 一个合理答案就可能实质改变行为、架构、安全、授权、数据处理或验收。
- **可逆假设：** 即使判断错误，也能以较低成本修正，不会造成有害外部影响或不兼容承诺。
- **非阻塞项：** 答案不影响当前修改边界。

只有阻塞项清空后才能继续。

## 先判断是在描述还是设计

对每个关键结论先问：

- 这是仓库已经实现的当前事实吗？
- 这是用户或权威规范接受的目标意图吗？
- 还是 Agent 根据现状推导出的候选方案？

运行结果、代码和测试可以高强度证明当前行为，但不能单独证明该行为符合用户期望。若任务正在定义“应该怎样工作”，而目标意图没有证据，必须把相关决策列为未知项。

## 提问前先检查

向用户提问前：

1. 搜索适用指令、代码、测试、契约、Schema、迁移、配置和近期相关历史。
2. 检查用户为本次操作提供的需求、原型、幻灯片、截图、设计稿和其他外部参考，并确认其适用范围。
3. 区分“信息不存在”和“信息只是难找”。
4. 不要求用户重复仓库中已经存在的事实，也不要求用户为当前实现背书。

## 提出高价值问题

一次只问一个问题。有效的问题应该：

- 指明尚未解决的决策；
- 简要说明可选方案；
- 说明已经找到的仓库证据；
- 解释答案将如何影响实施或验证。

用户不必已经知道完整答案。问题应从真实情境、目标和完成信号开始；必要时给出少量候选方案、例子或低成本原型，明确标记为 `proposed`，让用户通过选择、拒绝或修正使意图逐步浮现。

证据支持时给出推荐。不要盘问那些可以安全回退的偏好，也不要要求用户预先设计文件、页面或技术结构。

“继续追问到 95% 信心”可以作为避免臆测的提示，但放行标准必须是可检查的：所有会实质改变行为或验收的阻塞项已经解决。不要把主观百分比写成完成证据。

## 按后果升级

以下情况必须明确解决：

- 破坏性或不可逆操作；
- 生产变更或外部沟通；
- 身份验证、授权、密钥、资金、个人数据或安全；
- 公共契约和不可逆迁移；
- 超出用户明确范围的操作。

## 就绪摘要

需要可见摘要时，使用与项目文档相同的语言，并保持以下字段语义：

```text
目标：
已知：
阻塞项：
可逆假设：
验收证据：
授权：
结论：READY | BLOCKED
```

除非仓库已有规范位置，否则摘要只服务于当前任务。
