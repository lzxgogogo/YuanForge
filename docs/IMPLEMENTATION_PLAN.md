# 实施计划

> Yuan Layer 角色：交付
> 事实源：YuanForge 的稳定建设顺序、验证关卡和发布条件
> 不负责：当前任务状态和历史活动记录
> 更新时机：里程碑顺序、验收关卡或发布策略改变

## P0：可安装 Skill

- 提供合法的 `SKILL.md`、参考文档和 UI 元数据。
- 用中文 README 说明边界、安装和四种操作。
- 通过 Codex Skill 结构校验。

验收：仓库 Skill 与安装副本一致；相对链接和 SVG 有效。

## P1：项目自举

- 建立精炼的 `AGENTS.md`、`progress.txt`、`lessons.md`。
- 复用 README 和 Yuan Layer 文档承担已有规格职责。
- 明确技术边界、Worktree 策略和建设顺序。
- 修复可重复安装，建立可确定的仓库契约测试。
- 建立来源证明门和 Worktree 生命周期判断；区分候选评审、维护者授权、Git 集成和稳定分支验证。

验收：测试和 Skill 校验通过；Worktree 指南符合真实拓扑；没有重复事实源；`[Done]`/`READY` 不由未提交或候选分支证据支持。

## P2：行为评测

- 覆盖新项目、中途项目、只审计、漂移修复和偏好演化，并包含软件、研究、数据和文档仓库画像。
- 分开验证新项目的意图发现和已有项目的现状审计；链接、PPT、原型和对话不得被误记为已有项目事实。
- 覆盖“现有实现丰富但目标用户旅程缺失”的中途 UI 项目，验证 Agent 不会从页面、API 或后端流程猜测产品意图。
- 验证“用户不必预知完整意图；YuanForge 通过问题、候选和确认让意图浮现；确认后才写稳定目标文档”。
- 验证缺少领域能力时只推荐可选 Skill 组合并报告 `PARTIAL`，不把领域执行扩张进核心。
- 使用独立 Codex 任务运行 `evals/cases.json`，保存原始产物和差异。
- 根据跨项目证据修订 Skill，不从单个仓库静默泛化规则。
- 评测候选 Worktree 误报完成、脏状态保护、干净候选 `PARK` 和集成责任边界。

验收：每个核心操作至少有一个前向验证结果；失败能够归因到 Skill、项目证据或外部限制。

## P3：稳定发布

- 在不同类型、语言和复杂度的真实仓库中验证。
- 明确兼容范围、升级方式和已知限制。
- 发布前检查当前树、Git 历史、远端元数据和敏感文本。

验收：重要主张有新鲜证据；未验证范围在 README 和 `progress.txt` 中披露。
