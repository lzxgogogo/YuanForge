# 六类项目职责

YuanForge 固定的是信息职责，不是软件项目文件名。先识别项目类型和已有事实源，再为每类职责选择唯一规范位置。

## 第一性职责

| 职责 | 回答的问题 | 通用默认名 |
|---|---|---|
| 意图 | 为什么做、边界是什么、怎样算完成 | `docs/PROJECT_BRIEF.md` |
| 流程 | 谁在什么条件下做什么、状态如何变化、失败后如何恢复 | `docs/WORKFLOW.md` |
| 方法 | 使用哪些方法、工具、环境、数据和约束 | `docs/METHODS.md` |
| 交互 | 项目怎样与用户、参与者、系统或受众发生关系 | `docs/INTERACTION_GUIDE.md` |
| 结构 | 内部对象、模块、证据、数据和责任怎样组织 | `docs/PROJECT_STRUCTURE.md` |
| 交付 | 以什么顺序产出什么，并通过哪些验证关卡 | `docs/DELIVERY_PLAN.md` |

“交互”是外部表面，“结构”是内部组织。Frontend 和 Backend 只是软件项目中这两类职责的常见实现。

## 按项目选择表达

| 职责 | 软件开发 | 研究 | 数据与文档 |
|---|---|---|---|
| 意图 | PRD、需求与验收 | 研究问题、假设、范围 | 目标、受众、问题和成功条件 |
| 流程 | 用户旅程、业务生命周期、状态和异常路径 | 研究流程、决策点和偏差处理 | 数据管道、编辑流程和评审 |
| 方法 | 技术栈、运行环境、依赖 | 方法论、样本、数据源、工具 | 分析方法、来源、格式和工具 |
| 交互 | UI、API、CLI、可访问性 | 参与者接触、引用、结果呈现 | 查询接口、叙事、引用和呈现 |
| 结构 | 架构、模块、数据归属 | 证据、数据、笔记和分析结构 | Schema、目录、章节和资料关系 |
| 交付 | 实施、测试、发布 | 采集、分析、复现、评审 | 数据发布、审校、发布和归档 |

项目可以组合多个画像，例如研究型软件或数据驱动文档。只有主要事实、产物和验证能够进入仓库时，才属于 YuanForge 当前范围；不要用画像掩盖外部状态不可见的问题。

## 区分三种流程

“流程”不能成为所有步骤的杂物箱。先区分：

| 类型 | 核心问题 | 常见归属 |
|---|---|---|
| 产品或参与者旅程 | 人从入口到完成目标，经过哪些页面、状态和决策 | 流程职责；软件中常用 `APP_FLOW.md` 或 `PRODUCT_FLOW.md` |
| 业务或系统处理流 | 系统、服务、数据或研究对象怎样流转 | 流程职责的独立章节或独立规范 |
| Agent 或交付流程 | 项目如何规划、实施、验证和发布 | 交付职责、`AGENTS.md` 或 Worktree 指南 |

同一文件可以承载相邻流程，但必须明确边界。不得用业务后端流水线替代用户旅程，也不得用开发步骤替代产品行为。

## 用户交互型软件画像

仓库包含面向人的页面、桌面界面、移动端、交互式 CLI 或同类入口时，必须为产品旅程找到一个规范归属。至少覆盖：

- 角色与入口；
- 页面或交互表面；
- 用户动作与下一状态；
- 分支、成功和结束条件；
- 加载、空状态、错误和恢复；
- 路由、菜单与权限关系。

API、启动器、外部系统和视觉原则属于交互职责，但仅列这些内容不能证明用户旅程已经覆盖。现有实现可以证明“现在是什么”，不能单独证明“应该是什么”。

## 选择规则

1. 优先复用项目已经维护的规范文档。
2. 一个文件可以承担多个相邻职责，但必须声明边界。
3. 一个长期事实只能有一个规范归属。
4. 不适用的职责应在覆盖表中说明原因，不创建空文档。
5. 只有职责确实缺失时，才使用通用默认名或项目画像中的惯用名。
6. 安全、伦理、隐私、合规和证据质量放入最相关的职责；影响多个职责时，由 Agent 入口路由，但不复制全文。
