# 项目基线建立与恢复

当用户要求建立、重建或修复项目文档和 Git Worktree 时使用本流程。实际产出结构，不要只做描述。

## 检查当前项目

创建任何内容前：

1. 运行 `git worktree list`、`git branch --show-current` 和 `git status --short`。
2. 阅读适用的 `AGENTS.md`、`CLAUDE.md`、README、已有进度文件和仓库指令。
3. 搜索已跟踪文件和隐藏文件中的目标、流程、方法、结构、计划、代码、契约、测试、数据、来源、研究材料、输出和 Worktree 指南；同时检查用户为本次操作提供的原型、幻灯片、截图和设计资料。
4. 把现有产物映射到下方的信息职责。
5. 找出冲突、脏改动、路径碰撞、已被签出的分支和仍未验证的事实。

缺少预期文件名不等于缺少信息；信息分散也不应该成为拒绝建立规范结构的理由。

## 选择文档语言

写文档前先选择输出语言，优先级如下：

1. 用户对本次操作的明确语言要求；
2. 仓库中的明确语言规则；
3. 当前维护的 `AGENTS.md`、README 和稳定规格的主导语言；
4. 当前对话中用户使用的语言；
5. 没有更强信号时才默认英文。

只统计仍在维护的事实源。不要让旧文档、生成文件、依赖说明或代码注释的数量压过当前规范。

以下内容通常保持原样：文件名、命令、代码标识符、API/MQTT 字段、Schema 名称、品牌名和翻译后会降低精度的技术术语。

如果仓库有意按受众区分语言，例如中文产品文档配英文 API 契约，应保留这种分工。不要只为统一语言而批量翻译已有规范文档。证据冲突且会导致大范围重写时，先提出一个有依据的问题。

用户明确表达了长期语言偏好时，把规则精炼地写入已有项目指导；不要为此新建独立语言配置文件。

## 选择新项目或已有项目路径

- 新项目没有可供还原的当前实现。把用户提供的链接、PPT、原型、草稿和对话当作目标素材，读取 `references/intent-discovery.md`，在关键选择获得确认后建立初始规范。
- 已有项目先从代码、测试、运行结果、数据、产物和 Git 重建当前事实，再与已确认目标对照。
- 混合项目逐项分类，不因为实现证据丰富就假定目标已经明确。

用户不必预先说清完整意图。YuanForge 可以提出候选方案、例子或低成本原型帮助意图浮现，但最终写入稳定目标文档的关键取舍必须获得确认。

## 区分当前事实与目标意图

建立基线前，把关键主张分为四类：

- **当前事实：** 代码、测试、运行结果和现有产物证明现在怎样工作。
- **目标意图：** 已确认的需求、设计、研究方案或用户决定说明应该怎样工作。
- **候选方案：** Agent 或历史资料提出但尚未接受的变化。
- **待确认偏好：** 会影响体验、行为或验收，但没有可靠答案。

代码和测试通常是当前行为的强证据，但不能自动覆盖已确认的目标意图。历史原型、截图、幻灯片和外部设计资料是候选意图证据；先确认其适用版本和权威性，再把它们写入规范。

当目标意图缺失且一个合理答案可能改变范围、用户路径、公开行为、安全、数据或验收时，读取 `references/intent-discovery.md` 和 `references/readiness.md`，一次只问一个高价值问题。问题应指出已找到的素材或当前证据和仍待决定的目标。直到阻塞项清空后再把目标文档标为完成；用户明确要求早期草稿时使用 `To confirm` 并返回 `PARTIAL`。

## 建立六类稳定职责

按照 `references/roles.md` 选择或组合项目画像。固定以下职责，但文件名和内容必须跟随项目证据：

| 职责 | 最小内容 | 通用默认路径 |
|---|---|---|
| 意图 | 目标、范围、非目标、成功条件、开放问题 | `docs/PROJECT_BRIEF.md` |
| 流程 | 角色、入口、步骤、状态、失败和恢复 | `docs/WORKFLOW.md` |
| 方法 | 方法、工具、环境、数据、约束和可复现命令 | `docs/METHODS.md` |
| 交互 | 用户、参与者、系统或受众的外部接口和体验 | `docs/INTERACTION_GUIDE.md` |
| 结构 | 内部对象、模块、证据、数据、责任和边界 | `docs/PROJECT_STRUCTURE.md` |
| 交付 | 阶段、依赖、产物、验证关卡、发布或评审 | `docs/DELIVERY_PLAN.md` |

软件项目可以继续使用 `PRD.md`、`APP_FLOW.md`、`TECH_STACK.md`、Frontend、Backend 和 `IMPLEMENTATION_PLAN.md` 等惯用名，但不能把这些名称强加给研究、数据或文档项目。职责不适用时说明原因，不得虚构内容或创建空文件。

对用户交互型项目，目标旅程至少明确角色、触发情境、用户目标、完成信号和关键失败责任。页面、路由、菜单、权限、组件、API 和后端流水线可以证明当前实现或候选表达，但不能替用户决定目标。意图尚未确认时先走 `intent-discovery.md`，不要用页面清单填满目标文档。

从当前证据填充文档：

- 必要时引用仓库相对路径和命令。
- 使用 `必须`、`应`、`可以`、`待确认`，或仓库已有的同等规范词汇。
- 分开当前事实、已接受设计、计划和未决问题。
- 无证据主张标为“待确认”，不得用看似合理的架构填空。
- 优先精炼、可维护的文档，而不是穷尽式生成文本。
- 更新已有规范等价物，不建立第二套事实源。
- 新写的自然语言遵循已选择的项目语言。

已有不同名称的文档承担某项职责时，保留并从基线链接它；只有用户批准后才迁移。不得静默重命名或删除。

## 建立持久上下文循环

六类职责之外，始终单独创建或修复：

| 文件 | 用途 |
|---|---|
| `AGENTS.md` | Agent 入口和精炼路由；约 60 行是膨胀审查信号 |
| `progress.txt` | 当前实施状态、阻塞、下一步和未验证外部事实 |
| `lessons.md` | 可复用错误及其症状、根因和预防规则 |

根目录 `AGENTS.md` 应链接稳定文档，不复制完整 PRD、架构、契约、进度或 Lessons。约 60 行不是硬性门槛；不可约简的安全约束和复杂仓库路由可以保留。

只使用仓库需要的章节：

```text
# <项目> Agent 指南
## 开工顺序
## Worktree 路由
## 关键约束
## 最小验证
## 完成标准
```

嵌套 `AGENTS.md` 只作为子树特有覆盖，不复制根文件。

根 `AGENTS.md` 超过约 60 行时，检查重复事实、背景说明、示例、历史和子树规则是否应移出。不得为了行数截断规则或改写未决事实。

默认阅读顺序：

1. Worktree 和仓库状态；
2. `docs/WORKTREE_GUIDE.md`；
3. `lessons.md`；
4. `progress.txt`；
5. 与任务相关的稳定规格；
6. 目标代码、测试、契约、迁移和配置。

维护方式：

- 在重要里程碑、新阻塞或交接时，把 `progress.txt` 重写为精炼的当前快照。包含已完成、进行中、阻塞、下一步、验证和未验证外部事实，不把它变成追加日志。
- 只有具体错误、失败假设或流程纠正形成可复用规则时，才写入 `lessons.md`。记录症状、根因、预防和证据，不复制临时进度。
- 已有规范等价物时保留它们，并让 `AGENTS.md` 指向准确路径。只在用户约定要求时创建薄兼容文件。

## 建立 Worktree 指南

创建或修复 `docs/WORKTREE_GUIDE.md`，写清 Worktree 角色、准确路径、分支规则、变更流、集成要求和清理规则。它必须与实际创建的拓扑一致。

## 建立 Worktree 拓扑

优先遵循仓库已有 Worktree 指令，否则使用以下角色。角色是路由约定，不是必须同时存在的 Worktree 配额：

| 角色 | 目的 | 默认分支 | 默认同级目录 |
|---|---|---|---|
| `main` | 稳定集成基线 | 已有默认分支 | 当前仓库 |
| `experiment` | 高风险修改和原型 | `codex/experiment` | `<repo>-experiment` |
| `writing` | 规格和交付文档 | `codex/writing` | `<repo>-writing` |
| `agent-debug` | 可丢弃排查 | `codex/agent-debug` | `<repo>-agent-debug` |

添加 Worktree 前：

1. 写明一个独立目标、负责人或授权人、稳定基线和退出条件；没有这些信息不物化 Worktree。
2. 解析仓库根目录、默认分支、父目录和准确目标路径。
3. 保留所有未提交修改；未经明确批准不得移动或 Stash。
4. 角色、分支和状态匹配时复用已有 Worktree。
5. 分支已存在且未在其他位置签出时，为它添加 Worktree。
6. 分支不存在时，从已验证的稳定基线创建。
7. 遇到路径碰撞、基线歧义或分支已在其他 Worktree 签出时停止。

只创建当前操作需要或用户明确要求的 Worktree。没有对应任务时，在指南中把角色标记为“按需”，不得为了凑齐默认拓扑创建空闲 Worktree。

解析准确名称后，典型命令如下：

```bash
git worktree add -b codex/experiment ../<repo>-experiment <stable-branch>
git worktree add -b codex/writing ../<repo>-writing <stable-branch>
git worktree add -b codex/agent-debug ../<repo>-agent-debug <stable-branch>
```

分支已存在时：

```bash
git worktree add ../<repo>-writing codex/writing
```

不得只为匹配拓扑而删除 Worktree、分支或目录。干净且已提交的候选可以在 `PARK` 判断下移除实体 Worktree 并保留分支；脏 Worktree 默认保护。Worktree 移除、分支删除和成果放弃是独立授权动作。

## 验证基线

验证并报告：

1. `git worktree list` 显示当前实体 Worktree；指南中的未创建角色明确标记为“按需”。
2. 每个新 Worktree 具有预期基线，且状态干净或已披露。
3. 六个跨领域信息职责各有唯一规范归属或有证据的不适用说明。
4. `AGENTS.md`、`progress.txt`、`lessons.md` 存在或有明确等价物，并正确链接。
5. 已检查根 `AGENTS.md` 的精炼程度，超过参考值有运行或安全理由。
6. `docs/WORKTREE_GUIDE.md` 与真实拓扑一致，且公共仓库不提交个人绝对路径。
7. 相对链接可解析。
8. 命令、版本和默认值与仓库一致。
9. 新写自然语言符合所选项目语言，精度敏感标识符未被误译。
10. 无证据的外部或生产事实仍明确标为未验证。
11. 当前事实、目标意图和候选方案没有混写。
12. 用户交互型项目的关键目标已经确认，或明确披露缺失并进入意图发现流程。

返回精炼覆盖表，表头和状态说明使用项目语言，状态令牌保持稳定：

```text
职责                     规范产物                              状态
意图                     docs/PROJECT_BRIEF.md                已创建
流程                     docs/WORKFLOW.md                     已更新
方法                     docs/METHODS.md                      已复用
交互                     docs/INTERACTION_GUIDE.md            待确认
结构                     docs/PROJECT_STRUCTURE.md            已创建
交付                     docs/DELIVERY_PLAN.md                已创建
Agent 入口               AGENTS.md                            已更新
当前进度                 progress.txt                         已创建
可复用 Lessons           lessons.md                          已创建
Worktree 指南            docs/WORKTREE_GUIDE.md               已更新
Worktree 拓扑            git worktree list                    已验证
```

根据实际产物和新鲜验证使用 `READY`、`PARTIAL` 或 `BLOCKED`，不得仅根据计划判定。
