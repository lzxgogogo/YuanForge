# UI 证据画像

当项目包含 Web、桌面、移动端、交互式 CLI 或其他面向人的软件入口，且需要建立或审计产品旅程时使用。先按 `domain-evidence.md` 组织证据，再由 YuanForge 决定规范归属。

## 目标

重建 **As-built UI**，识别 **Intended UI** 的证据，并报告差异。不要从组件或页面名称猜测用户目标。

## 选择检查模式

| 模式 | 可以可靠回答 | 主要限制 |
|---|---|---|
| `source-only` | 路由、组件、状态分支、权限、接口调用 | 不能证明实际渲染和目标体验 |
| `runtime` | 可见页面、真实跳转、反馈和部分异常状态 | 隐藏分支和权限组合可能未覆盖 |
| `artifact-only` | 编译产物中的页面、文案、路由和请求线索 | 组件边界、死代码和设计原因不清楚 |
| `mixed` | 源码、运行时和产品资料的交叉验证 | 仍需确认资料版本和用户意图 |

无法启动项目时不要为了截图修改生产配置、绕过鉴权或伪造数据。使用现有测试、Story、Fixture 或安全的本地环境；模拟结果必须标明。

## 重建当前 UI

按以下顺序检查：

1. 入口：登录、默认路由、深链、桌面启动器、移动入口。
2. 导航：路由表、菜单、重定向、返回行为和权限守卫。
3. 表面：页面、弹窗、抽屉、向导、交互式命令和关键组件。
4. 动作：按钮、表单、快捷键、自动触发和批量操作。
5. 状态：初始、加载、空、成功、失败、超时、无权限、离线和恢复。
6. 数据：接口、缓存、本地状态、轮询、WebSocket 和提交后的刷新。
7. 角色：可见入口、可执行动作、交接对象和最终确认责任。

源码说明可能分支，运行时说明本次实际观察。两者不一致时记录冲突。

## 重建产品旅程

每条主旅程使用以下结构：

```text
角色：
触发情境：
用户目标：
入口：
步骤：
  1. <表面> — <用户动作> — <系统反馈> — <用户判断> — <下一状态>
成功与结束：
失败与恢复：
交接：
证据：
状态：confirmed | inferred | conflicting
```

至少检查：

- 正常完成路径；
- 一个最高影响的异常或恢复路径；
- 权限或角色导致的分支；
- 用户怎样知道任务已经完成；
- 当前路径与产品资料是否一致。

## 识别目标意图

目标证据可来自已确认的 PRD、产品流程、原型、设计稿、讲义、用户访谈和评审记录。代码、测试和运行界面默认只证明当前实现。

遇到以下情况必须报告阻塞项：

- 当前页面存在，但无法确认是否应保留；
- 多份产品资料描述不同目标路径；
- 角色、完成条件或异常责任不明确；
- 一个合理答案会改变页面结构、公开行为或验收。

问题从任务情境开始，不从“你想要哪些页面”开始。优先询问：

> 谁在什么情境下，因为发生了什么而开始这次任务，最终凭什么判断已经完成？

随后一次只追问一个仍会改变行为或验收的决策。
