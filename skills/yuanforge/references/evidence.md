# 证据门槛

“完成”是一项主张。每项重要主张都必须由当前仓库状态产生的证据支持。

## 证据强度

适用时按以下顺序优先选择证据：

1. 在目标环境或目标行为上的当前执行结果。
2. 覆盖本次修改行为的新鲜自动化测试。
3. 契约、Schema、类型、迁移或静态验证。
4. 对当前 Diff 和实现的精确检查。
5. 文档或历史证据。
6. 假设或模型推理。

较低等级可以解释结论，但不能自动替代所需的更高等级证据。

## 新鲜度

证据在以下条件下才算新鲜：

- 在相关修改之后产生；
- 适用于当前工作树或提交；
- 环境和覆盖范围明确；
- 结果与失败状态可见。

未运行测试时明确写“未运行”。无法运行时给出准确阻塞原因。不得用过去的成功结果暗示当前修改已通过。

## 主张—证据检查

对每项重要的完成声明，检查：

1. 具体主张是什么？
2. 哪个产物或执行结果可以证伪它？
3. 本次是否实际检查或执行了该证据？
4. 是否覆盖修改行为和重要失败路径？
5. 哪些内容仍不在覆盖范围内？

## 常见过度声明

避免以下替代：

- 用“代码看起来正确”代替行为测试。
- 用“可以编译”代替运行时正确性。
- 用“单元测试通过”代替集成或外部系统行为。
- 用“请求已发布”代替设备或下游已经执行。
- 用“模拟器通过”代替现场或生产验证。
- 用“没有出现错误”代替已检查的验收条件。

## 证据回执格式

使用项目文档的语言给出精炼报告：

```text
结论：READY | PARTIAL | BLOCKED | NOT READY

主张：
- <主张> — <支持证据>

验证：
- <命令或检查> — <结果>

未验证：
- <缺失检查及原因>

残余风险：
- <已知限制或外部条件>
```

不要用与重要主张无关的日常细节填充报告。
